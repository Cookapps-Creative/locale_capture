# CookApps Locale Capture

한 번 플레이를 기록하면, 지원 언어마다 같은 플레이를 다시 재생하며 영상으로 녹화한다. 로비·전투·상점·가챠가 언어마다 같은 장면으로 나온다.
게임 코드를 하나도 참조하거나 고치지 않는다. 에디터 전용(빌드에 들어가지 않는다).

## 설치

1. `LocaleCapture.unitypackage` 를 가져온다(Assets → Import Package → Custom Package). `Assets/CookApps/LocaleCapture` 에 들어간다.
2. 컴파일 뒤 `Creative > Locale Capture` 를 열어 맨 위가 "점검 통과" 인지 본다.

게임 쪽에 넣을 코드나 패치는 없다.

## 사용

1. `Creative > Locale Capture` → 언어 체크, 해상도·품질, Output File 의 File Name·Path → **녹화 대기**.
2. Unity **Play** 를 직접 누른다. 대기를 누르면 플레이 화면이 Device Simulator 로 바뀌고, 언어별 재생은 자동으로 Game 뷰에서(기록 때 화면 크기·안전 영역 그대로), 끝나면 다시 Simulator 로 돌아온다. Resolution 이 Custom 이면 그 크기 그대로의 Simulator 기기(`LocaleCapture 1080x1920` 등, 노치 없음)를 `Devices/` 에 만들어 자동으로 고른다 — 영상이 출력 크기로 바로 나와 블러·늘림이 없다. Custom 이 아니면 Simulator 에서 고른 기기 그대로이고, 기기 비율이 출력 비율과 다르면 편집 Export 의 비율·Blur 로 맞춘다. 빌드 설정의 첫 씬(켜진 씬이 없으면 목록 첫 씬)부터 열리고, 부팅부터 기록된다.
3. 원하는 장면에서 **START** → 플레이 → **STOP**. START 부터 STOP 까지만 녹화된다. START 전에는 STOP 이 없고, START 전에 Play 를 끄면 취소된다. 녹화 중 인스펙터에서 오브젝트·컴포넌트 체크박스(켜기/끄기)를 바꾸면 그 순간이 기록돼 언어별 영상에도 같은 프레임에 반영된다(UI 숨기기 등). Input 의 **바로 녹화** 를 켜 두면 START 없이 Play 부터 녹화가 시작되고 STOP 만 누른다.
4. 언어마다 플레이 모드가 자동으로 다시 열리며 부팅부터 같은 플레이를 재생하고, START 이후만 녹화한다. BGM·SFX 스템은 앞 언어 패스들이 함께 뽑아(첫 언어 = SFX, 둘째 = BGM) 따로 패스를 돌지 않고, 끝나면 그 영상들의 소리를 다시 섞어 원래대로 둔다. 언어에 따라 다른 음성·효과음이 있는 게임은 Audio 의 **언어별 SFX(음성)** 를 켠다 — 모든 언어 패스가 자기 SFX 스템(`audio_sfx.<언어>.wav`)을 뽑고 BGM 은 영상 없는 가벼운 패스로 하나 뽑는다(패스 +1). 편집 창·Export 도 언어마다 자기 SFX 스템을 쓴다. 편집은 창 맨 아래 **Edit Videos** 로 연다.
   Input 의 **빠른 녹화**(기본 켜짐)는 언어별 재생을 30fps 실제 속도로 묶지 않고 기기가 낼 수 있는 만큼 빨리 돌린다. 영상·소리는 프레임마다 만들어져 결과물 속도는 같다. 녹화와 달라졌거나 앞 언어와 다른 플레이가 된 언어는 실제 속도로 다시 뽑는다(한 언어당 3번까지, 결과에 "다시 —" 로 남는다 — 아래 "자동으로 다시 뽑기"). 끄면 예전처럼 첫 입력 전 부팅 구간만 빨리 돌리고 나머지는 실제 속도다. 재생 동안 Game 뷰를 최대화하고(다른 창이 매 프레임 그리지 않게, 끝나면 되돌림), 영상에 남지 않는 구간(START 전·스템 패스)은 URP 렌더 스케일을 0.1 로 낮춰 그린다(화면 좌표·UI 레이아웃은 그대로). 패스마다 걸린 시간은 콘솔에 `재생 …프레임에 …초` 로 남는다.
   런타임 패치 대상은 `Library/LocaleCapture/patch-targets.json` 에 캐시해, 코드가 다시 빌드되기 전까지 녹화 대기가 바로 끝난다.
5. 창 오른쪽 위 **⋮ → Re-render…** 는 이미 있는 기록을 지금 설정으로 다시 뽑는다. 다시 플레이하지 않고, 서버도 필요 없다.
6. 어긋난 언어가 있거나 중간에 끊겼으면(취소 포함) 창 맨 위 결과 아래에 **다시 뽑기 — <언어들>** 버튼이 나온다. 누르면 맞게 나오지 못한 언어만 같은 기록·같은 설정으로 다시 뽑는다 — 다시 플레이하지 않고, 맞게 나온 언어의 영상은 그대로 둔다. 스템(BGM·SFX)을 함께 뽑던 언어를 다시 뽑으면 그 스템도 다시 뽑아 그 스템을 쓰는 영상 모두에 다시 섞는다. 플레이 검사는 모두 통과했는데 영상 비교에서만 다른 영상이 나온 경우에는 어느 언어 영상이 틀렸는지 알 수 없어 언어 영상을 모두 다시 뽑는다.

결과: `<Path>/<File Name>_<시각>/<File Name>_<시각>_<언어>.mp4`, 스템 `audio_bgm.wav`·`audio_sfx.wav`, 진단 `verify/*.json`. 언어 영상은 모두 프레임 수가 같다(START 부터 STOP 까지, 소리가 조금 짧아도 영상 프레임을 자르지 않는다).

## 언어마다 같은 플레이가 되는 방법

| 맞추는 것 | 방법 |
|---|---|
| 시작 상태 | 기록 시작 때 persistentDataPath·temporaryCachePath·PlayerPrefs 를 통째로 백업하고, 재생 직전마다 복원. 기록과 모든 재생 패스는 플레이 모드에 들어갈 때 도메인과 씬을 다시 올린다 — Enter Play Mode Settings 로 리로드를 꺼 둔 프로젝트도 작업 동안만 켜고 끝나면 되돌린다(정적 필드의 캐시·싱글턴·초기화 여부가 앞 플레이에서 넘어오면 패스마다 로딩 개수와 타이밍이 달라진다). 그만큼 패스마다 진입이 느려진다 |
| 서버 결과(가챠·보상·인벤토리) | 부팅부터 서버 응답(HttpClient·UnityWebRequest)을 지연 프레임까지 기록했다가 재생 때 그대로 돌려줌. HttpClient 응답은 기록 때도 재생과 같은 자리(세션 Update)에서 게임에 넘긴다 — 실제 응답은 작업 스레드에서 끝나 게임이 이어받는 프레임이 실행마다 한두 프레임 다르고, HttpClient 안쪽(ConfigureAwait(false))이 스레드 풀을 한 번 더 거친다. 넘기는 동안 동기화 컨텍스트를 비워 그 이어받기가 그 자리에서 돌게 한다. 응답 없이 끝난 요청도 그대로 남긴다 — 예외로 끝난 것(연결 실패)은 재생에서도 같은 프레임에 예외로, 취소된 것(타임아웃·화면을 떠나며 취소)은 취소로, 기록이 끝날 때까지 안 끝난 것은 재생에서도 끝나지 않게 한다(UnityWebRequest 는 테이프 서버가 응답 없이 연결을 끊어 응답 코드 0 의 연결 오류로 끝난다 — 오류 문구는 기록 때와 다를 수 있다). 작업 스레드에서 보낸 HttpClient 요청(`Task.Run` 안의 요청 등)은 재생에서도 작업 스레드에서 응답을 넘긴다 — 그 뒤 메인 스레드로 돌아오는 것은 아래 "작업 스레드" 가 프레임을 맞춘다 |
| 기록보다 많은 요청 | 재생에서 같은 요청이 기록보다 많이 나가면 실제 서버로 보내지 않고 그 요청의 마지막 기록 응답으로 대신(연결 대기 화면·실제 계정 변경 방지). 기록에 아예 없는 요청(예: 녹화 땐 캐시를 써서 안 나간 요청)은 실제 서버에서 받되, 받는 동안 게임 시간을 멈춰 그 뒤 흐름이 밀리지 않게 하고 언어별 테이프에 남김 |
| 언어별 서버 데이터 | 요청에 언어 코드가 든 요청은 그 언어로 처음 뽑을 때만 실서버, 이후 언어별 테이프로 재생. 주소의 언어 표기만 다른 녹화 요청(`locale=ko` ↔ `locale=en`·`zh-Hant`)이 있으면 응답은 그 요청이 녹화에서 도착한 프레임에 넘긴다(일찍 오면 붙잡고, 늦으면 게임 시간을 멈추고 기다림) |
| 시간 | 프로젝트 코드의 DateTime·TickCount, 모든 스크립트와 Assets 의 DLL(DOTween 등)의 realtimeSinceStartup·Stopwatch·unscaled 시간·소리 시계(dspTime)·Task.Delay(메인 스레드)를 "기록 시작 시각 + 프레임/fps" 로 바꿔치기. 코루틴의 WaitForSecondsRealtime 도 같은 시계로 돈다. 프로젝트 코드의 Stopwatch 인스턴스(Start·Elapsed 등)도 같은 시계로 돌아, "프레임당 몇 ms 썼으면 다음 프레임으로" 식으로 일을 나누는 코드가 기기 부하와 상관없이 늘 같은 프레임에 끝난다(세션 시계는 한 프레임 안에서 흐르지 않는다. 패키지·DLL 의 Stopwatch 는 그대로). 기록은 실제 1/fps 초 간격, 재생은 빠른 녹화면 묶지 않는다. UI Toolkit(엔진 모듈)도 같은 시계로 돈다 — 런타임 패널의 전환 애니메이션·예약 실행(schedule)·더블 클릭 판정과 스크롤 관성이 재생 속도와 상관없이 녹화와 같은 프레임에 진행된다(에디터 창은 자기 시계를 따로 써서 영향이 없다) |
| 작업 스레드 | 작업 스레드에서 메인 스레드로 돌아오는 이어받기(await Task.Run, UniTask.RunOnThreadPool·SwitchToMainThread, Addressables 의 handle.Task·Task.WhenAll 완료 등)를 붙잡아, 기록 때 넘긴 프레임에 재생에서도 넘긴다(일찍 오면 붙잡고, 아직이면 메인 스레드를 잠깐 세워 기다린다). Unity 동기화 컨텍스트의 Post 와 UniTask 의 AddContinuation 을 다른 스레드에서 부른 것만 대상이고, 에디터 쪽 코드의 것은 손대지 않는다 |
| 난수 | 프로젝트 코드의 new Random()·Guid, BCL Random 생성자, UnityEngine.Random 시드 고정. new Random() 시드는 "만든 코드(타입.메서드) + 그 코드가 만든 몇 번째" 로 정하고, 에디터·다른 스레드가 만든 것은 세지 않는다 — 프레임 번호로 정하면 흐름이 한 프레임만 밀려도 덱 셔플·뽑기가 통째로 바뀐다(이전 형식 기록을 다시 뽑을 때만 예전 방식). 소리 코드(호출 경로에 Audio·Sound 가 든 타입)가 쓰는 UnityEngine.Random 은 따로 둔 상태로 돌려, 소리 재생 개수 차이가 게임 판정 난수를 흔들지 않게 한다 |
| 화면 | 기록 때의 안전 영역·DPI·노치를 재생에 그대로 줌 — Device Simulator 로 기록하고 게임뷰에서 재생해도 UI 배치가 같다 |
| 입력 | Input System 은 이벤트 트레이스, 예전 Input 은 게임이 물은 값을 프레임별 기록. 기록 때도 실제 장치 입력을 가로채 가상 장치로 프레임 시작에 넣는다(재생과 같은 시점) — 손을 뗀 순간이 게임 Update 사이에 처리돼 "뗐다"를 놓치는 일이 녹화에만 생기지 않게 |
| 로딩 시간 차이 | 씬·Addressables·비동기 작업 완료를 기록해, 재생 때 같은 로딩이 끝날 때까지 게임 시간을 멈춤(씬은 실제로 읽는 중일 때만. 기다린 프레임의 난수 소비는 되돌림). 씬을 일찍 다 읽으면 기록 때 열린 프레임까지 활성화를 미룸. 에디터의 Addressables(Use Asset Database) 가 로드마다 넣는 가짜 지연(Simulated Load Delay)은 세션 동안 0 으로 둔다 — 실제 빌드에는 없는 지연이고 시계에 묶여 있어, 로딩 대기와 얽히면 로드가 안 끝나거나 일찍 끝난다. 완료 콜백 안에서 시작해 바로 끝난 다음 로드는 다음 프레임으로 미루지 않고 같은 프레임에 이어서 끝낸다(연쇄 단계 수가 언어마다 달라도 걸리는 프레임이 같게). 기다리는 동안에는 세션 시계로 끝나는 것(`Task.Delay`, 테이프 응답)도 같이 멈춘다 — 로딩만 늦은 것이면 풀린 뒤 녹화와 같은 프레임에 이어진다. 씬·서버 응답이 아닌 로딩을 2초 넘게 기다려도 안 풀리면(그 로딩으로 가는 길에 대기·응답이 있는 경우 — 흐름이 이미 녹화와 다르다) 그 시계들을 따로 돌려 풀고, 결과에 "로딩" 으로 남긴다. 기다리는 프레임마다 게임 시간이 아주 조금(2^-17초) 흐르는데, 대기가 풀린 다음 프레임을 그만큼 짧게 해 되돌린다 — 엔진 시간(`Time.time`)이 녹화와 다시 같아져, `Time.time + 1초` 처럼 프레임 경계에 딱 걸리는 게임 타이머가 한 프레임 일찍·늦게 끝나지 않는다 |
| 언어 전환 | 저장 값 안의 녹화 언어 표기(ko-KR·Korean 등)를 재생 언어로 바꾸고, 기기 언어와 UI 문화권(CurrentUICulture)도 그 언어로. 그래도 다르면 부팅이 끝난 뒤(START 이후) Unity Localization·I2 선택 언어를 바꿈. 도구가 선택 언어를 읽을 때는 게임이 언어 시스템 초기화를 끝낸 뒤에만 읽는다(Unity Localization 은 읽기만 해도 진행 중인 초기화를 그 자리에서 끝낸다). 그 언어로 처음 뽑느라 실제 서버에서 받은 응답이 있었던 패스는 받아 둔 응답으로 한 번 더 뽑는다(결과에 "다시 —") |
| BGM·SFX 분리 | 반복 재생하는 10초 이상 소리를 BGM 으로 보고 패스마다 끔 |

바꿔치기는 녹화·재생 동안에만 Harmony(동봉, MIT)로 건다. 시간을 프로젝트 코드에서만 바꾸는 건 패키지의 네트워크 서명처럼 실제 시각이 필요한 곳을 건드리지 않기 위해서다.

## 일치 검사

작업이 끝나면 창 맨 위(점검 줄 자리)에 "최근 녹화 성공/실패" 가 나오고, 실패면 그 아래 작은 글씨로 **어느 프레임부터 무엇이 달라졌는지**가 나온다. 자세한 결과는 콘솔과 `verify/<패스>.json`, 실패 보고서에 남는다.

기준은 **녹화 시작(START) 이후 녹화와 프레임 하나도 다르지 않게 재생됐는가**다. 허용 오차는 없다 — 덱 셔플처럼 한 프레임 차이가 다른 플레이로 번지는 곳이 있다. 패스마다 아래를 녹화와 프레임 단위로 맞춰 보고, 처음 달라진 프레임과 분류를 결과에 적는다.

| 분류 | 보는 것 |
|---|---|
| 터치 | 누른 순간 그 입력을 실제로 받은 UI(누르기·클릭·드래그 처리기). 언어마다 문구가 길어져 다른 그래픽이 맞아도 받는 대상이 같으면 같은 터치. 로딩 대기로 한 프레임이 여러 번에 걸쳐 돌 때 눌린 것도 놓치지 않는다 |
| UI | 입력을 받을 수 있는 UI(버튼·카드 등)가 켜지고 꺼지고 잠긴 프레임 — 흐름이 밀리거나 당겨진 첫 프레임이 여기서 드러난다 |
| 화면 | 최상위 Canvas 가 열리고 닫힌 프레임 |
| 난수 | 매 프레임 끝의 UnityEngine.Random 상태 |
| 난수 생성 | `new Random()` 이 만들어진 프레임과 만든 코드 |
| 서버 | 요청이 나간 프레임, 녹화보다 많이·적게 나간 요청 |
| 입력 | 재생한 입력이 모두 게임에 들어갔는지 |
| 스레드 | 작업 스레드에서 돌아오는 이어받기가 녹화 프레임에 왔는지(기다려도 안 오면 달라진 것) |
| 로딩 | 로딩이 끝난 프레임(원인을 짚는 참고 — 이것만으로는 실패로 보지 않는다) |

- **다름**(실패): START 이후에 위 분류 중 하나라도 달라졌거나, 언어 패스끼리 난수 상태 흐름이 달랐거나, 영상 비교에서 한쪽만 화면이 바뀌거나 다른 화면이 나왔다. 영상 패스가 끝났는데 그 언어 영상 파일이 새로 만들어지지 않은 경우(인코더 실패·디스크·파일이 다른 프로그램에 열려 있음)와 소리를 다시 섞지 못한 경우도 실패다.
- **주의**(성공으로 치고 작은 글씨로 알림): 영상 비교에서 화면이 바뀌는 정도가 조금 달랐다 / 프로젝트 코드에 바꿔 끼우지 못한 시계·난수 호출이 있다 / 이전 형식 기록에서 누른 곳의 맨 위 그래픽이 달랐다.
- 창의 결과 상자 아래에는 중단된 까닭(실패한 경우)과 "다름"·"주의" 줄이 작은 글씨로 나온다. 직접 취소한 작업은 실패로 치지 않고 보고서도 만들지 않는다.
- **참고**: START 전에 이미 달랐던 곳(영상에는 안 남지만 그 뒤 흐름을 밀 수 있다), 로딩 시점 차이.

**자동으로 다시 뽑기**: 재생이 녹화와 달라진 언어는 그 언어만 실제 속도로 다시 뽑는다(결과에 "다시 —"). 간헐적인 어긋남은 다시 뽑으면 대개 맞으므로 한 언어당 3번까지 다시 뽑는다 — 판정 기준은 그대로다(프레임 하나라도 다르면 실패). 실제 속도 재생이 두 번 연달아 같은 곳에서 어긋나면 그 기록에서는 늘 그런 것으로 보고 더 뽑지 않는다(결과에 "참고 —", 그 언어는 "다름"). 어긋난 시도의 검사 결과는 `verify/<언어>.fast.json`(빠른 재생)·`<언어>.try<N>.json`(실제 속도) 으로 남는다. 영상 파일이 만들어지지 않은 경우(인코더가 죽음 등)에도 그 언어를 다시 뽑는다.

**멈춤 감시**: 언어별 재생이 더 나아가지 않으면 — 세션 프레임이 90초 동안 그대로이거나, 플레이 모드에서 120초 동안 재생이 시작되지 않으면 — 그 패스를 끊고 다시 뽑는다(위 한도 안에서). 재생 중 에디터가 일시정지되면(Console 의 Error Pause 등) 풀고 이어 간다. 플레이 모드에 60초 동안 들어가지 못하면(컴파일 오류) 실패로 끝낸다. 에디터 메인 스레드가 통째로 멈춘 경우는 알아채지 못한다.

**영상 비교**: 모든 패스가 끝나면 언어 영상을 프레임마다 서로 비교한다(나온 영상 자체로 하는 마지막 확인). 화면을 가로 64픽셀 회색으로 줄여 두 가지를 본다.
- 화면이 바뀌는 시점: 프레임마다 "앞 프레임에서 얼마나 바뀌었나"를 영상별로 재서 맞춰 본다. 같은 플레이면 언어가 달라도 같은 프레임에 같은 만큼 바뀐다(가만히 있는 글자는 값에 안 잡힌다). 두 영상의 값 차이에서 큰 쪽의 25%(글자 양 차이)를 뺀 값이 2.5 이상이면 다름, 1.2 이상이면 주의. 재본 값은 같은 플레이 0.1 이하(가장 큰 것 0.85), 갈라진 플레이 2.9~76.
- 화면 모양: 닮은 정도(PSNR)의 1초 평균이 16dB 아래면 다름(팝업 유무·다른 장면 — 처음부터 다른 화면이라 바뀌는 시점으로는 안 잡히는 경우). 글자가 큰 화면(챕터 제목·상점)은 같은 플레이도 22dB 까지 내려가므로 그 사이 값으로는 판정하지 않는다.
- 언어 영상의 프레임 수가 서로 다르면 주의로 알린다.

이전 형식 기록(UI·난수 생성 타임라인이 없는 기록)을 다시 뽑으면 그 둘은 비교하지 않고, 누른 곳은 맨 위 그래픽으로만 가린다.

## 실패 보고

테이크가 중단되거나 녹화와 다르게 재생되면 보고서를 창의 Output File > Path 폴더(기본 `Recordings/LocaleCapture/`)에 `<시각>_<녹화>.md` 로 남긴다 — 결과 메시지, 패스별 일치 검사 요약, 설정, 환경, 이 도구 태그가 붙은 콘솔 줄. 게임 로그와 계정 정보는 담지 않는다.

## 편집

편집 창은 창 맨 아래 **Edit Videos** 로 연다(다른 녹화는 창 오른쪽 위 **⋮ → 다른 녹화 편집…**). 한 언어 영상을 보면서 지정한 편집은 모든 언어 영상에 똑같이 적용된다.

- 창 구성: 미리보기 → 재생 줄 → 타임라인 → **구간** 줄(In/Out·선택 해제) → **편집** 줄(Delete·Mute▾·Fade·Speed·Insert Clip) → **출력** 줄(Frame·Target·내보낼 비율·Thumbnail·Export) → 편집 목록
- 구간 선택: 타임라인 트랙(Video/BGM/SFX)을 **드래그**하면 바로 구간이 잡힌다. 눈금자를 누르거나 끌면 재생 위치만 옮긴다. In/Out 손잡이를 끌어 조정하고, **우클릭**하면 구간 편집 메뉴(삭제·음소거·페이드·배속)가 뜬다. I/O 키도 그대로 된다
- **삭제 구간 접기**(재생 줄 오른쪽, 기본 켜짐): 지운 부분을 타임라인에서 얇은 빨간 줄로 접는다. 줄을 눌러 고르고 Del 로 되살릴 수 있다. 끄면 원래 길이로 펼친다
- 구간 → **Delete**(삽입 클립 안 구간도 지운다), **Mute BGM**·**Mute SFX**·**Mute All**(삽입 클립 안 구간에도 걸린다. 클립에 스템(audio_bgm.wav·audio_sfx.wav)이 없으면 BGM/SFX 음소거는 그 구간 클립 소리 전체 음소거로 적용), **Speed**(슬라이더 0.1x–10x, 0.1 단위. 삽입 클립 안 구간에도 걸리고, 소리도 같은 배속으로 미리듣기·내보내기), **Fade In-Out**(F 키, 구간 앞 절반은 검게 어두워지고 뒤 절반은 다시 밝아짐 — 원래 화면 → 검정 → 원래 화면. 결과 영상 기준이라 구간 안의 삭제 부분은 빼고 남은 길이에서 계산하며, 사이의 삽입 클립도 함께 덮는다. 삽입 클립 안에도 In/Out 을 둘 수 있다)
- **Insert Clip**: 재생 위치 앞에 다른 영상(언어별로 다르게도). Locale Capture 녹화 클립은 BGM·SFX 를 따로 끈다
- **Frame**: 비율별 Blur(안에 맞추고 빈 곳 블러)·Crop(자르기, 위치 조절) 미리보기
- **Target** 목표 길이, 실행 취소 Ctrl+Z·Ctrl+Y
- **Thumbnail**: 플레이헤드 장면을 언어별·비율별 PNG
- **Export**: 비율 토글(9:16·1:1·16:9·4:5)마다 언어별 파일. 포맷·품질·해상도는 Locale Capture 창 설정을 따른다
- 녹화 인코딩과 편집·내보내기는 동봉 ffmpeg(`Tools/ffmpeg.exe`, GPL 빌드 — `FFMPEG-LICENSE.txt`). 녹화는 ffmpeg 를 별도 프로세스로 띄워 프레임을 흘려 보내므로 게임이 인코딩을 기다리지 않고, GPU 인코더(NVENC·AMF·QSV)가 되면 자동으로 쓴다(콘솔에 `GPU 인코더 … 사용`). ffmpeg 가 없으면 Unity 내장 인코더로 떨어진다

## 전제와 한계

- 언어 목록은 Unity Localization·I2 Localization 에서 읽는다. 둘 다 없으면 창의 Language Codes 에 직접 적는다.
  언어를 저장 값에 독자 형식으로 두는 게임은 창의 **Language Pref Key** 에 그 PlayerPrefs 키를 적는다.
- HTTP 가 아닌 통신(소켓·WebSocket), 네이티브 플러그인 내부 상태는 기록하지 못한다.
- 제네릭 타입의 메서드나 `catch … when` 이 든 메서드처럼 바꿔 끼우지 못한 곳은 그 안의 시계·난수·입력 호출이 원래대로 돈다. 테이크의 `verify/patch-problems.txt` 에 메서드와 남은 호출이 모두 적히고, 결과에 "주의 — 패치"(프로젝트가 직접 쓴 코드의 시계·난수 생성·입력이 남음) 또는 "참고 — 패치"(게임 난수, 패키지·`Assets/Plugins` 코드만 남음) 로 나온다.
- 로딩을 기다리는 동안 게임 Update 가 더 돈다. 프레임 수를 세는 로직은 어긋날 수 있고, 일치 검사가 알려 준다.
- 시계 값(DateTime·TickCount)을 그대로 난수 시드로 쓰는 코드는 흐름이 한 프레임만 달라도 시드가 달라진다. 도구가 따로 고정하는 것은 `new Random()`·Guid·UnityEngine.Random 뿐이다.
- Stopwatch 를 세션 시계로 돌리는 것은 프로젝트 코드(Assets 아래 소스)의 호출만이다. 패키지·DLL 안에서 실제 시간으로 일을 나누는 코드는 그대로다.
- UnityWebRequest 로 받는 응답은 녹화 프레임에서 한 프레임쯤 앞뒤로 올 수 있다(HttpClient 응답은 정확히 같은 프레임).
- 입력 기록은 새 Input System 패키지(`com.unity.inputsystem`)를 쓴다 — 패키지가 없는 프로젝트에서는 컴파일되지 않는다.
- 작업 스레드에서 돌아오는 이어받기를 맞추는 것은 Unity 동기화 컨텍스트와 UniTask 를 거치는 것만이다. 게임이 따로 만든 메인 스레드 큐(Update 에서 꺼내 도는 방식)나 네이티브 SDK 콜백은 그대로다.
- 로딩을 기다리는 동안(씬 로드·실서버 응답) 게임 시간은 멈추지만 Update 는 돈다 — 그 사이 프레임 수로 진행하는 로직은 녹화보다 앞설 수 있고, 일치 검사가 알려 준다.
- 터치·UI 검사는 uGUI(GraphicRaycaster) 기준이다. UI Toolkit 패널을 누른 터치는 "패널이 눌렸다" 까지만 비교하고(패널 안의 어느 요소인지는 보지 않는다), 3D 오브젝트를 직접 레이캐스트하는 입력은 그 검사에 잡히지 않는다(난수·서버·영상 비교는 그대로 본다).
- 플레이(입력·난수·UI·서버)가 녹화와 같아도 화면 한 프레임이 언어 영상끼리 다르게 찍히는 일이 있다. 이 게임의 부팅 스플래시(로고 뒤 흰색 페이드)에서 관찰했다 — 씬 로드 직전의 오래 걸리는 프레임(80~600ms)에서 한쪽 패스의 페이드가 한 프레임 늦게 그려졌다가 다음 프레임에 따라잡았다. 원인은 확인하지 못했다(도구가 맞추는 시계·로딩 순서는 두 패스가 같았다). 그 프레임이 영상 구간 안이고 화면이 크게 바뀌는 중이면 영상 비교가 "다름" 으로 잡고, 창의 "다시 뽑기" 로 언어 영상을 다시 뽑으면 된다. 부팅 구간은 보통 START 전이라 영상에 들어가지 않는다.
- Addressables 는 Play Mode Script 가 "Use Asset Database" 일 때를 기준으로 맞추고 검증했다. "Use Existing Build"(번들) 모드는 검증하지 못했다 — 번들·에셋 로딩이 실제 파일을 읽는 시간만큼 프레임이 지나서 끝나는데, 재생에서 녹화보다 늦게 끝나면 기다려 맞추지만 일찍 끝나는 것은 맞추지 않는다(씬 활성화만 미룬다). 그래서 로딩이 끝나는 프레임이 달라져 어긋날 수 있다(어긋나면 일치 검사에 잡힌다).
- 영상 비교의 기준값은 세로 화면 카드 게임 한 종에서 잰 것이다(같은 플레이 30쌍, 갈라진 플레이 5쌍). 언어마다 길이가 크게 다른 글자가 화면 가득 한꺼번에 나타나는 장면은 같은 플레이도 주의가 나올 수 있다.
- 입력 기록 버퍼는 필요한 만큼 늘어난다(한도 512MB). 한도를 넘으면 그 기록은 저장하지 않고 실패로 알린다.
- 기록과 재생은 같은 게임뷰 크기여야 한다(창이 자동으로 맞춘다).
- Windows 에디터 기준(PlayerPrefs 백업에 reg.exe 를 쓴다).
- 프로젝트에 다른 Harmony(0Harmony.dll)가 있으면 하나만 남긴다.
