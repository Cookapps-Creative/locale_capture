# CookApps Locale Capture

플레이를 한 번 기록하면, 지원 언어마다 같은 플레이를 다시 재생해 언어별 영상으로 뽑는 Unity 에디터 도구다.

- 로비·전투·상점·가챠가 언어마다 같은 장면으로 나온다.
- 게임 코드를 참조하거나 고치지 않는다.
- 에디터 전용이라 빌드에 들어가지 않는다.

| 녹화하는 사람 | [설치](#설치) · [녹화](#녹화) · [결과 확인](#결과-확인) · [다시 뽑기](#다시-뽑기) · [편집](#편집) |
| 도구를 고치는 사람 | [전제와 한계](#전제와-한계) · [동작 원리](#동작-원리) |

## 설치

1. `LocaleCapture.unitypackage` 를 가져온다(Assets → Import Package → Custom Package). `Assets/CookApps/LocaleCapture` 에 들어간다.
2. 컴파일이 끝나면 `Creative > Locale Capture` 를 열어 맨 위가 "점검 통과" 인지 본다.

게임 쪽에 넣을 코드나 패치는 없다.

## 녹화

### 순서

1. `Creative > Locale Capture` 에서 언어를 체크하고 해상도·품질, Output File 의 File Name·Path 를 정한다.
2. **녹화 대기** 를 누른다.
3. Unity **Play** 를 직접 누른다. 빌드 설정의 첫 씬(켜진 씬이 없으면 목록 첫 씬)부터 열린다.
4. 원하는 장면에서 **START** → 플레이 → **STOP**.
5. 기다린다. 언어마다 플레이 모드가 자동으로 다시 열려 부팅부터 같은 플레이를 재생하고, START 이후만 녹화한다.
6. 창 맨 위에 "최근 녹화 성공/실패" 가 나온다. 편집은 창 맨 아래 **Edit Videos** 로 연다.

알아 둘 것:

- 기록은 부팅부터 하지만 영상에는 START 부터 STOP 까지만 남는다.
- START 전에는 STOP 이 없다. START 전에 Play 를 끄면 취소된다.
- 녹화 중 인스펙터에서 오브젝트·컴포넌트 체크박스(켜기/끄기)를 바꾸면 그 순간이 기록돼, 언어별 영상에도 같은 프레임에 반영된다(UI 숨기기 등).
- 녹화나 언어별 재생이 도는 동안 다른 프로그램을 써도 된다. 게임은 포커스를 잃은 것을 모른다(아래 "앱 포커스").

### 옵션

| 옵션 | 하는 일 |
|---|---|
| Input > **바로 녹화** | START 없이 Play 부터 녹화한다. STOP 만 누른다 |
| Input > **빠른 녹화** (기본 켜짐) | 언어별 재생을 30fps 실제 속도로 묶지 않고 기기가 낼 수 있는 만큼 빨리 돌린다. 영상·소리는 프레임마다 만들어져 결과물 속도는 같다 |
| Audio > **언어별 SFX(음성)** | 언어에 따라 음성·효과음이 다른 게임에서 켠다. 언어마다 자기 SFX 스템을 뽑는다(패스 +1) |
| **Language Codes** | Unity Localization·I2 Localization 이 둘 다 없는 프로젝트에서 언어 목록을 직접 적는다 |
| **Language Pref Key** | 언어를 저장 값에 독자 형식으로 두는 게임에서 그 PlayerPrefs 키를 적는다 |

빠른 녹화를 끄면 예전처럼 첫 입력 전 부팅 구간만 빨리 돌리고 나머지는 실제 속도로 재생한다.

### 화면 크기

녹화 대기를 누르면 플레이 화면이 Device Simulator 로 바뀐다. 언어별 재생은 Game 뷰에서 자동으로 돌고(기록 때 화면 크기·안전 영역 그대로), 끝나면 다시 Simulator 로 돌아온다.

| Resolution | Simulator 기기 | 결과 |
|---|---|---|
| Custom | 그 크기 그대로의 기기(`LocaleCapture 1080x1920` 등, 노치 없음)를 `Devices/` 에 만들어 자동으로 고른다 | 영상이 출력 크기로 바로 나와 블러·늘림이 없다 |
| 그 밖 | Simulator 에서 고른 기기 그대로 | 기기 비율이 출력 비율과 다르면 편집 Export 의 비율·Blur 로 맞춘다 |

### 소리 스템

- BGM·SFX 스템은 앞 언어 패스들이 함께 뽑는다(첫 언어 = SFX, 둘째 = BGM). 스템만을 위한 패스는 따로 돌지 않는다.
- 끝나면 그 영상들의 소리를 다시 섞어 원래대로 둔다.
- **언어별 SFX(음성)** 를 켜면 모든 언어 패스가 자기 SFX 스템(`audio_sfx.<언어>.wav`)을 뽑고, BGM 은 영상 없는 가벼운 패스로 하나 뽑는다. 편집 창·Export 도 언어마다 자기 SFX 스템을 쓴다.

### 결과물

```
<Path>/<File Name>_<시각>/
├─ <File Name>_<시각>_<언어>.mp4    언어별 영상
├─ audio_bgm.wav · audio_sfx.wav    소리 스템
└─ verify/*.json                    일치 검사 결과
```

언어 영상은 모두 프레임 수가 같다. START 부터 STOP 까지이고, 소리가 조금 짧아도 영상 프레임을 자르지 않는다.

## 결과 확인

작업이 끝나면 창 맨 위(점검 줄 자리)에 "최근 녹화 성공/실패" 가 나온다.

- 결과 상자 아래에 작은 글씨로 중단된 까닭(실패한 경우)과 "다름"·"주의" 줄이 나온다.
- "다름" 줄에는 **어느 프레임부터 무엇이 달라졌는지**가 적힌다.
- 자세한 결과는 콘솔, `verify/<패스>.json`, 실패 보고서에 남는다.

### 판정

기준은 **녹화 시작(START) 이후 녹화와 프레임 하나도 다르지 않게 재생됐는가**다. 허용 오차는 없다. 덱 셔플처럼 한 프레임 차이가 다른 플레이로 번지는 곳이 있기 때문이다.

**다름** — 실패. 아래 중 하나라도 해당하면 실패다.

- START 이후에 [검사 분류](#검사-분류) 중 하나라도 녹화와 달라졌다.
- 언어 패스끼리 난수 상태 흐름이 달랐다.
- 영상 비교에서 한쪽만 화면이 바뀌거나 다른 화면이 나왔다.
- 영상 패스가 끝났는데 그 언어 영상 파일이 새로 만들어지지 않았다(인코더 실패·디스크·파일이 다른 프로그램에 열려 있음).
- 소리를 다시 섞지 못했다.

**주의** — 성공으로 치고 작은 글씨로 알린다.

- 영상 비교에서 화면이 바뀌는 정도가 조금 달랐다.
- 프로젝트 코드에 바꿔 끼우지 못한 시계·난수 호출이 있다.
- 이전 형식 기록에서 누른 곳의 맨 위 그래픽이 달랐다.

**참고** — 실패로 치지 않고 원인을 짚는 데 쓴다.

- START 전에 이미 달랐던 곳(영상에는 안 남지만 그 뒤 흐름을 밀 수 있다).
- 로딩 시점 차이.

직접 취소한 작업은 실패로 치지 않고 보고서도 만들지 않는다.

### 검사 분류

패스마다 아래를 녹화와 프레임 단위로 맞춰 보고, 처음 달라진 프레임과 분류를 결과에 적는다.

| 분류 | 보는 것 |
|---|---|
| 터치 | 누른 순간 그 입력을 실제로 받은 UI(누르기·클릭·드래그 처리기) |
| UI | 입력을 받을 수 있는 UI(버튼·카드 등)가 켜지고 꺼지고 잠긴 프레임 |
| 화면 | 최상위 Canvas 가 열리고 닫힌 프레임 |
| 난수 | 매 프레임 끝의 UnityEngine.Random 상태 |
| 난수 생성 | `new Random()` 이 만들어진 프레임과 만든 코드 |
| 서버 | 요청이 나간 프레임, 녹화보다 많이·적게 나간 요청 |
| 입력 | 재생한 입력이 모두 게임에 들어갔는지 |
| 스레드 | 작업 스레드에서 돌아오는 이어받기가 녹화 프레임에 왔는지(기다려도 안 오면 달라진 것) |
| 로딩 | 로딩이 끝난 프레임 |

- **터치**: 언어마다 문구가 길어져 다른 그래픽이 맞아도, 받는 대상이 같으면 같은 터치로 본다. 로딩 대기로 한 프레임이 여러 번에 걸쳐 돌 때 눌린 것도 놓치지 않는다.
- **UI**: 흐름이 밀리거나 당겨진 첫 프레임이 여기서 드러난다.
- **로딩**: 원인을 짚는 참고다. 이것만으로는 실패로 보지 않는다.
- **이전 형식 기록**(UI·난수 생성 타임라인이 없는 기록)을 다시 뽑으면 UI·난수 생성은 비교하지 않고, 누른 곳은 맨 위 그래픽으로만 가린다.

### 영상 비교

모든 패스가 끝나면 언어 영상을 프레임마다 서로 비교한다. 나온 영상 자체로 하는 마지막 확인이다. 화면을 가로 64픽셀 회색으로 줄여 두 가지를 본다.

**화면이 바뀌는 시점**

- 프레임마다 "앞 프레임에서 얼마나 바뀌었나"를 영상별로 재서 맞춰 본다.
- 같은 플레이면 언어가 달라도 같은 프레임에 같은 만큼 바뀐다(가만히 있는 글자는 값에 안 잡힌다).
- 두 영상의 값 차이에서 큰 쪽의 25%(글자 양 차이)를 뺀 값으로 판정한다. 2.5 이상이면 다름, 1.2 이상이면 주의다.
- 재본 값은 같은 플레이 0.1 이하(가장 큰 것 0.85), 갈라진 플레이 2.9~76 이다.

**언어별 화면 배치 차이는 다름으로 치지 않는다**

글자 길이·줄 높이가 언어마다 달라, 같은 플레이라도 한 언어에서만 UI 배치가 다시 잡히는 프레임이 있다. 예: 팝업이 새로 고쳐지는 순간 중국어 화면만 목록 줄 간격이 바뀐다. 그 프레임은 그 언어 영상만 더 많이 바뀌어 위 기준을 넘는다.

- 재생 패스마다 **UI 배치 계산으로 자리·크기가 실제로 바뀐 프레임**을 적어 둔다(`verify/<언어>.json` 의 `Layouts`). uGUI 가 배치를 다시 계산하는 자리(LayoutRebuilder)에서 앞뒤를 잰 것이라, 애니메이션·스크롤로 움직인 것은 들어가지 않는다.
- 영상 비교가 걸린 프레임에 **더 많이 바뀐 쪽 언어에서만 배치가 움직였으면** 그 프레임은 판정에서 빼고, 결과에 "참고 — 영상 비교: …초에 zh-CN 화면만 UI 배치가 크게 움직였다" 로 남긴다.
- 빼지 않는 경우:
  - 양쪽 언어의 배치가 비슷하게 움직였다(차이가 큰 쪽의 25% 이하). 화면만 한 프레임 늦게 그려진 경우가 여기 든다.
  - 덜 바뀐 쪽에서만 배치가 움직였다, 또는 배치가 그 프레임(과 바로 앞 프레임)이 아닌 때에 움직였다.
  - 배치 기록이 없는 영상이다(이전 버전으로 뽑았거나, 배치 추적이 꺼졌다).
- 뺀 프레임 뒤도 끝까지 본다. 플레이가 갈린 것이면 그다음 프레임들에서 다름이 난다.
- 배치를 uGUI 배치 계산이 아니라 게임 코드가 직접 옮기는 UI 는 기록에 안 잡혀, 예전처럼 다름으로 나온다.

**화면 모양**

- 닮은 정도(PSNR)의 1초 평균이 16dB 아래면 다름이다. 팝업 유무·다른 장면처럼 처음부터 다른 화면이라 바뀌는 시점으로는 안 잡히는 경우를 잡는다.
- 글자가 큰 화면(챕터 제목·상점)은 같은 플레이도 22dB 까지 내려가므로 그 사이 값으로는 판정하지 않는다.

언어 영상의 프레임 수가 서로 다르면 주의로 알린다.

### 실패 보고서

테이크가 중단되거나 녹화와 다르게 재생되면 보고서를 남긴다.

- 위치: 창의 Output File > Path 폴더(기본 `Recordings/LocaleCapture/`)의 `<시각>_<녹화>.md`
- 내용: 결과 메시지, 패스별 일치 검사 요약, 설정, 환경, 이 도구 태그가 붙은 콘솔 줄
- 게임 로그와 계정 정보는 담지 않는다.

## 다시 뽑기

아래는 모두 다시 플레이하지 않고, 이미 있는 기록으로 뽑는다.

### 자동으로 다시 뽑기

- 녹화와 달라졌거나 앞 언어와 다른 플레이가 된 언어는 그 언어만 실제 속도로 다시 뽑는다(결과에 "다시 —").
- 한 언어당 3번까지다. 간헐적인 어긋남은 다시 뽑으면 대개 맞는다.
- 판정 기준은 그대로다(프레임 하나라도 다르면 실패).
- 실제 속도 재생이 두 번 연달아 같은 곳에서 어긋나면 그 기록에서는 늘 그런 것으로 보고 더 뽑지 않는다(결과에 "참고 —", 그 언어는 "다름").
- 영상 파일이 만들어지지 않은 경우(인코더가 죽음 등)에도 그 언어를 다시 뽑는다.
- 어긋난 시도의 검사 결과는 `verify/<언어>.fast.json`(빠른 재생)·`<언어>.try<N>.json`(실제 속도)으로 남는다.

### 멈춤 감시

| 상황 | 처리 |
|---|---|
| 세션 프레임이 90초 동안 그대로다 | 그 패스를 끊고 다시 뽑는다(위 한도 안에서) |
| 플레이 모드에서 120초 동안 재생이 시작되지 않는다 | 그 패스를 끊고 다시 뽑는다(위 한도 안에서) |
| 재생 중 에디터가 일시정지됐다(Console 의 Error Pause 등) | 풀고 이어 간다 |
| 플레이 모드에 60초 동안 들어가지 못한다(컴파일 오류) | 실패로 끝낸다 |
| 에디터 메인 스레드가 통째로 멈췄다 | 알아채지 못한다 |

### 다시 뽑기 버튼

어긋난 언어가 있거나 중간에 끊겼으면(취소 포함) 창 맨 위 결과 아래에 **다시 뽑기 — <언어들>** 버튼이 나온다.

- 맞게 나오지 못한 언어만 같은 기록·같은 설정으로 다시 뽑는다. 맞게 나온 언어의 영상은 그대로 둔다.
- 스템(BGM·SFX)을 함께 뽑던 언어를 다시 뽑으면 그 스템도 다시 뽑아, 그 스템을 쓰는 영상 모두에 다시 섞는다.
- 플레이 검사는 모두 통과했는데 영상 비교에서만 다른 영상이 나왔으면 언어 영상을 모두 다시 뽑는다. 어느 언어 영상이 틀렸는지 알 수 없기 때문이다.

### Re-render

창 오른쪽 위 **⋮ → Re-render…** 는 이미 있는 기록을 지금 설정으로 다시 뽑는다. 서버도 필요 없다.

## 편집

편집 창은 창 맨 아래 **Edit Videos** 로 연다. 다른 녹화는 창 오른쪽 위 **⋮ → 다른 녹화 편집…** 으로 연다.

한 언어 영상을 보면서 지정한 편집은 모든 언어 영상에 똑같이 적용된다.

### 창 구성

위에서부터 미리보기 → 재생 줄 → 타임라인 → 구간 줄 → 편집 줄 → 출력 줄 → 편집 목록 순서다.

| 줄 | 들어 있는 것 |
|---|---|
| 구간 | In/Out·선택 해제 |
| 편집 | Delete·Mute▾·Fade·Speed·Insert Clip |
| 출력 | Frame·Target·내보낼 비율·Thumbnail·Export |

### 구간 선택

- 타임라인 트랙(Video/BGM/SFX)을 **드래그**하면 바로 구간이 잡힌다.
- 눈금자를 누르거나 끌면 재생 위치만 옮긴다.
- In/Out 손잡이를 끌어 조정한다. I/O 키도 그대로 된다.
- 구간을 잡고 타임라인을 **우클릭**하면 구간 편집 메뉴(삭제·음소거·페이드·배속)가 뜬다.

### 구간 편집

| 기능 | 하는 일 |
|---|---|
| **Delete** | 구간을 지운다 |
| **Mute BGM**·**Mute SFX**·**Mute All** | 구간의 소리를 끈다 |
| **Speed** | 슬라이더 0.1x–10x, 0.1 단위. 소리도 같은 배속으로 미리듣기·내보내기 |
| **Fade In-Out** (F 키) | 구간 앞 절반은 검게 어두워지고 뒤 절반은 다시 밝아진다(원래 화면 → 검정 → 원래 화면) |

- 네 기능 모두 삽입 클립 안 구간에도 걸린다(삽입 클립 안에도 In/Out 을 둘 수 있다).
- **Mute**: 클립에 스템(audio_bgm.wav·audio_sfx.wav)이 없으면 BGM/SFX 음소거는 그 구간 클립 소리 전체 음소거로 적용된다.
- **Fade In-Out**: 결과 영상 기준이다. 구간 안의 삭제 부분은 빼고 남은 길이에서 계산하며, 사이의 삽입 클립도 함께 덮는다.
- **삭제 구간 접기**(재생 줄 오른쪽, 기본 켜짐): 지운 부분을 타임라인에서 얇은 빨간 줄로 접는다. 줄을 눌러 고르고 Del 로 되살릴 수 있다. 끄면 원래 길이로 펼친다.

### 그 밖의 기능

| 기능 | 하는 일 |
|---|---|
| **Insert Clip** | 재생 위치 앞에 다른 영상을 넣는다(언어별로 다르게도). Locale Capture 녹화 클립은 BGM·SFX 를 따로 끈다 |
| **Frame** | 비율별 Blur(안에 맞추고 빈 곳 블러)·Crop(자르기, 위치 조절) 미리보기 |
| **Target** | 목표 길이 |
| **Thumbnail** | 플레이헤드 장면을 언어별·비율별 PNG 로 뽑는다 |
| **Export** | 비율 토글(9:16·1:1·16:9·4:5)마다 언어별 파일. 포맷·품질·해상도는 Locale Capture 창 설정을 따른다 |
| 실행 취소 | Ctrl+Z·Ctrl+Y |

### 인코더

- 녹화 인코딩과 편집·내보내기는 동봉 ffmpeg 를 쓴다(`Tools/ffmpeg.exe`, GPL 빌드 — `FFMPEG-LICENSE.txt`).
- 녹화는 ffmpeg 를 별도 프로세스로 띄워 프레임을 흘려 보내므로 게임이 인코딩을 기다리지 않는다.
- GPU 인코더(NVENC·AMF·QSV)가 되면 자동으로 쓴다(콘솔에 `GPU 인코더 … 사용`).
- ffmpeg 가 없으면 Unity 내장 인코더로 떨어진다.

## 전제와 한계

### 환경

- Windows 에디터 기준이다(PlayerPrefs 백업에 reg.exe 를 쓴다).
- 입력 기록은 새 Input System 패키지(`com.unity.inputsystem`)를 쓴다. 패키지가 없는 프로젝트에서는 컴파일되지 않는다.
- 프로젝트에 다른 Harmony(0Harmony.dll)가 있으면 하나만 남긴다.
- 기록과 재생은 같은 게임뷰 크기여야 한다(창이 자동으로 맞춘다).
- 입력 기록 버퍼는 필요한 만큼 늘어난다(한도 512MB). 한도를 넘으면 그 기록은 저장하지 않고 실패로 알린다.

### 언어

- 언어 목록은 Unity Localization·I2 Localization 에서 읽는다. 둘 다 없으면 창의 Language Codes 에 직접 적는다.
- 언어를 저장 값에 독자 형식으로 두는 게임은 창의 **Language Pref Key** 에 그 PlayerPrefs 키를 적는다.

### 맞추지 못하는 것

- **HTTP 가 아닌 통신**(소켓·WebSocket)과 네이티브 플러그인 내부 상태는 기록하지 못한다.
- **바꿔 끼우지 못한 메서드**: 제네릭 타입의 메서드나 `catch … when` 이 든 메서드는 그 안의 시계·난수·입력 호출이 원래대로 돈다.
  - 테이크의 `verify/patch-problems.txt` 에 메서드와 남은 호출이 모두 적힌다.
  - 결과에는 "주의 — 패치"(프로젝트가 직접 쓴 코드의 시계·난수 생성·입력이 남음) 또는 "참고 — 패치"(게임 난수, 패키지·`Assets/Plugins` 코드만 남음)로 나온다.
- **시계 값을 시드로 쓰는 난수**: 시계 값(DateTime·TickCount)을 그대로 난수 시드로 쓰는 코드는 흐름이 한 프레임만 달라도 시드가 달라진다. 도구가 따로 고정하는 것은 `new Random()`·Guid·UnityEngine.Random 뿐이다.
- **패키지·DLL 의 Stopwatch**: Stopwatch 를 세션 시계로 돌리는 것은 프로젝트 코드(Assets 아래 소스)의 호출만이다. 패키지·DLL 안에서 실제 시간으로 일을 나누는 코드는 그대로다.
- **UnityWebRequest 응답**은 녹화 프레임에서 한 프레임쯤 앞뒤로 올 수 있다(HttpClient 응답은 정확히 같은 프레임).
- **작업 스레드**: 돌아오는 이어받기를 맞추는 것은 Unity 동기화 컨텍스트와 UniTask 를 거치는 것만이다. 게임이 따로 만든 메인 스레드 큐(Update 에서 꺼내 도는 방식)나 네이티브 SDK 콜백은 그대로다.
- **로딩 대기 중의 Update**: 로딩을 기다리는 동안(씬 로드·실서버 응답) 게임 시간은 멈추지만 Update 는 돈다. 그 사이 프레임 수로 진행하는 로직은 녹화보다 앞설 수 있고, 일치 검사가 알려 준다.
- **Addressables 번들 모드**: Play Mode Script 가 "Use Asset Database" 일 때를 기준으로 맞추고 검증했다. "Use Existing Build"(번들) 모드는 검증하지 못했다.
  - 번들·에셋 로딩은 실제 파일을 읽는 시간만큼 프레임이 지나서 끝난다.
  - 재생에서 녹화보다 늦게 끝나면 기다려 맞추지만, 일찍 끝나는 것은 맞추지 않는다(씬 활성화만 미룬다).
  - 그래서 로딩이 끝나는 프레임이 달라져 어긋날 수 있다. 어긋나면 일치 검사에 잡힌다.

### 검사의 한계

- **uGUI 기준**: 터치·UI 검사는 uGUI(GraphicRaycaster) 기준이다.
  - UI Toolkit 패널을 누른 터치는 "패널이 눌렸다" 까지만 비교한다(패널 안의 어느 요소인지는 보지 않는다).
  - 3D 오브젝트를 직접 레이캐스트하는 입력은 그 검사에 잡히지 않는다(난수·서버·영상 비교는 그대로 본다).
- **영상 비교 기준값**은 세로 화면 카드 게임 한 종에서 잰 것이다(같은 플레이 30쌍, 갈라진 플레이 5쌍). 언어마다 길이가 크게 다른 글자가 화면 가득 한꺼번에 나타나는 장면은 같은 플레이도 주의가 나올 수 있다(한 언어에서만 UI 배치가 움직인 프레임은 [영상 비교](#영상-비교)가 가려낸다).
- **화면 한 프레임 차이**: 플레이(입력·난수·UI·서버)가 녹화와 같아도 화면 한 프레임이 언어 영상끼리 다르게 찍히는 일이 있다.
  - 이 게임의 부팅 스플래시(로고 뒤 흰색 페이드)에서 관찰했다. 씬 로드 직전의 오래 걸리는 프레임(80~600ms)에서 한쪽 패스의 페이드가 한 프레임 늦게 그려졌다가 다음 프레임에 따라잡았다.
  - 원인은 확인하지 못했다(도구가 맞추는 시계·로딩 순서는 두 패스가 같았다).
  - 그 프레임이 영상 구간 안이고 화면이 크게 바뀌는 중이면 영상 비교가 "다름" 으로 잡는다. 창의 "다시 뽑기" 로 언어 영상을 다시 뽑으면 된다.
  - 부팅 구간은 보통 START 전이라 영상에 들어가지 않는다.

## 동작 원리

언어마다 같은 플레이가 되도록 아래 항목을 녹화와 맞춘다.

- 바꿔치기는 녹화·재생 동안에만 Harmony(동봉, MIT)로 건다.
- 시간을 프로젝트 코드에서만 바꾸는 것은 패키지의 네트워크 서명처럼 실제 시각이 필요한 곳을 건드리지 않기 위해서다.

### 시작 상태

- 기록 시작 때 persistentDataPath·temporaryCachePath·PlayerPrefs 를 통째로 백업하고, 재생 직전마다 복원한다.
- 기록과 모든 재생 패스는 플레이 모드에 들어갈 때 도메인과 씬을 다시 올린다.
  - Enter Play Mode Settings 로 리로드를 꺼 둔 프로젝트도 작업 동안만 켜고 끝나면 되돌린다.
  - 정적 필드의 캐시·싱글턴·초기화 여부가 앞 플레이에서 넘어오면 패스마다 로딩 개수와 타이밍이 달라지기 때문이다.
  - 그만큼 패스마다 진입이 느려진다.

### 서버 결과 (가챠·보상·인벤토리)

- 부팅부터 서버 응답(HttpClient·UnityWebRequest)을 지연 프레임까지 기록했다가 재생 때 그대로 돌려준다.
- HttpClient 응답은 기록 때도 재생과 같은 자리(세션 Update)에서 게임에 넘긴다.
  - 실제 응답은 작업 스레드에서 끝나 게임이 이어받는 프레임이 실행마다 한두 프레임 다르고, HttpClient 안쪽(ConfigureAwait(false))이 스레드 풀을 한 번 더 거친다.
  - 넘기는 동안 동기화 컨텍스트를 비워 그 이어받기가 그 자리에서 돌게 한다.
- 작업 스레드에서 보낸 HttpClient 요청(`Task.Run` 안의 요청 등)은 재생에서도 작업 스레드에서 응답을 넘긴다. 그 뒤 메인 스레드로 돌아오는 것은 아래 [작업 스레드](#작업-스레드)가 프레임을 맞춘다.
- 응답 없이 끝난 요청도 그대로 남긴다.

  | 기록에서 | 재생에서 |
  |---|---|
  | 예외로 끝났다(연결 실패) | 같은 프레임에 예외로 끝낸다 |
  | 취소됐다(타임아웃·화면을 떠나며 취소) | 취소로 끝낸다 |
  | 기록이 끝날 때까지 안 끝났다 | 끝나지 않게 한다 |

  UnityWebRequest 는 테이프 서버가 응답 없이 연결을 끊어 응답 코드 0 의 연결 오류로 끝난다. 오류 문구는 기록 때와 다를 수 있다.

### 통신 코드는 재생에서도 그대로 돈다

HttpClient 는 요청을 처리 단계(DelegatingHandler)에 차례로 태우고, 맨 아래 단계가 실제로 서버와 주고받는다. 통신 라이브러리는 그 사이에서 복호화·서명 확인·봉투 풀기·오류 변환을 하고, 서버 시각이나 오류 정보처럼 응답 밖에 따로 남기는 값도 거기서 만든다.

- **맨 아래 단계의 원본 응답을 같이 기록한다.** 암호화·서명·봉투가 그대로인 서버 응답이다(테이프의 `Raws`).
- **재생에서는 처리 단계를 그대로 돌리고, 맨 아래에서만 서버 대신 원본 응답으로 답한다.** 게임이 응답에서 따로 꺼내 쓰는 값이 녹화와 같아진다.
  - 바깥에서 저장한 응답을 바로 돌려주면 처리 단계가 통째로 건너뛰어진다. 응답마다 서버 시각으로 시계를 맞추는 게임은 재생에서 시계가 한 번도 안 맞춰져, 시간으로 쌓이는 보상이 녹화와 다르게 나왔다.
- 어느 요청인지 고르는 일과 게임에 넘길 프레임을 맞추는 일은 그대로 바깥에서 한다.
- 처리 단계가 같은 원본 응답을 녹화와 다르게 처리하면(응답 코드·내용·예외가 다르면) 결과에 "서버" 로 남는다.
- 재생에서는 맨 아래가 요청 호출 안에서 바로 답한다. 처리 단계는 그 자리에서 끝까지 돌고, 게임은 녹화와 같은 프레임에 결과를 받는다.
  - 처리 단계가 응답을 받은 순간 화면을 직접 바꾼다면(게임이 결과를 받기 전에) 그 시점은 녹화보다 이르다.
- 원본 응답이 없는 요청은 예전처럼 바깥에서 바로 답한다: 이전 버전으로 녹화한 기록, 취소·미완료로 끝난 요청, 맨 아래 단계를 걸지 못한 경우(콘솔과 `verify/patch-problems.txt` 에 남는다).
- 패스별 결과의 `ServerPiped` 가 이 방식으로 답한 요청 수다. 0 이면 통신 코드가 건너뛰어진 것이다.

### 기록보다 많은 요청

- **같은 요청이 기록보다 많이 나가면** 실제 서버로 보내지 않고 그 요청의 마지막 기록 응답으로 대신한다(연결 대기 화면·실제 계정 변경 방지).
- **기록에 아예 없는 요청**(예: 녹화 땐 캐시를 써서 안 나간 요청)은 실제 서버에서 받는다. 받는 동안 게임 시간을 멈춰 그 뒤 흐름이 밀리지 않게 하고, 언어별 테이프에 남긴다.

### 언어별 서버 데이터

- 요청에 언어 코드가 든 요청은 그 언어로 처음 뽑을 때만 실서버에서 받고, 이후에는 언어별 테이프로 재생한다.
- 주소의 언어 표기만 다른 녹화 요청(`locale=ko` ↔ `locale=en`·`zh-Hant`)이 있으면, 응답은 그 요청이 녹화에서 도착한 프레임에 넘긴다(일찍 오면 붙잡고, 늦으면 게임 시간을 멈추고 기다림).

### 시간

아래 시계를 모두 "기록 시작 시각 + 프레임/fps" 로 바꿔치기한다.

| 범위 | 대상 |
|---|---|
| 프로젝트 코드 | DateTime·TickCount, Stopwatch 인스턴스(Start·Elapsed 등) |
| 모든 스크립트와 Assets 의 DLL(DOTween 등) | realtimeSinceStartup·Stopwatch.GetTimestamp·unscaled 시간·소리 시계(dspTime)·Task.Delay(메인 스레드) |
| 코루틴 | WaitForSecondsRealtime |
| UI Toolkit(엔진 모듈) | 런타임 패널의 전환 애니메이션·예약 실행(schedule)·더블 클릭 판정, 스크롤 관성 |

- 기록은 실제 1/fps 초 간격으로 돌고, 재생은 빠른 녹화면 묶지 않는다.
- 세션 시계는 한 프레임 안에서 흐르지 않는다. 그래서 "프레임당 몇 ms 썼으면 다음 프레임으로" 식으로 일을 나누는 코드가 기기 부하와 상관없이 늘 같은 프레임에 끝난다(패키지·DLL 의 Stopwatch 인스턴스는 그대로).
- UI Toolkit 은 재생 속도와 상관없이 녹화와 같은 프레임에 진행된다. 에디터 창은 자기 시계를 따로 써서 영향이 없다.
- 세션 프레임은 늘 같은 엔진 프레임(4번째)이 끝날 때부터 센다. 플레이 모드에 들어간 직후에는 화면이 아직 그려지지 않아 "프레임 끝" 신호가 한 번 빠지는 실행이 있는데, 첫 신호부터 세면 게임이 보는 `Time.time`·`Time.frameCount` 가 실행마다 한 프레임 달라진다.
  - 그러면 "`Time.time` 이 0.5초 지나면" 식의 게임 타이머가 프레임 경계에서 한 프레임 일찍·늦게 끝난다.
  - 재생은 녹화가 세기 시작한 엔진 프레임을 따른다. 다르게 시작했으면 결과에 "시간" 으로 남긴다.

### 작업 스레드

- 작업 스레드에서 메인 스레드로 돌아오는 이어받기를 붙잡아, 기록 때 넘긴 프레임에 재생에서도 넘긴다.
  - 일찍 오면 붙잡고, 아직이면 메인 스레드를 잠깐 세워 기다린다.
  - 예: await Task.Run, UniTask.RunOnThreadPool·SwitchToMainThread, Addressables 의 handle.Task·Task.WhenAll 완료.
- Unity 동기화 컨텍스트의 Post 와 UniTask 의 AddContinuation 을 다른 스레드에서 부른 것만 대상이다. 에디터 쪽 코드의 것은 손대지 않는다.

### 난수

- 프로젝트 코드의 new Random()·Guid, BCL Random 생성자, UnityEngine.Random 의 시드를 고정한다.
- new Random() 시드는 "만든 코드(타입.메서드) + 그 코드가 만든 몇 번째" 로 정한다. 에디터·다른 스레드가 만든 것은 세지 않는다.
  - 프레임 번호로 정하면 흐름이 한 프레임만 밀려도 덱 셔플·뽑기가 통째로 바뀐다.
  - 이전 형식 기록을 다시 뽑을 때만 예전 방식(프레임 번호)을 쓴다.
- 소리 코드(호출 경로에 Audio·Sound 가 든 타입)가 쓰는 UnityEngine.Random 은 따로 둔 상태로 돌린다. 소리 재생 개수 차이가 게임 판정 난수를 흔들지 않게 하기 위해서다.

### 화면

- 기록 때의 안전 영역·DPI·노치를 재생에 그대로 준다.
- Device Simulator 로 기록하고 게임뷰에서 재생해도 UI 배치가 같다.

### 입력

- Input System 은 이벤트 트레이스로, 예전 Input 은 게임이 물은 값을 프레임별로 기록한다.
- 기록 때도 실제 장치 입력을 가로채 가상 장치로 프레임 시작에 넣는다(재생과 같은 시점). 손을 뗀 순간이 게임 Update 사이에 처리돼 "뗐다"를 놓치는 일이 녹화에만 생기지 않게 하기 위해서다.
- 가로챈 입력은 실제 장치 상태를 바꾸지 않는다. 바뀌면 게임이 실제 장치(그 프레임)와 가상 장치(다음 프레임)를 둘 다 보는데, 재생에는 가상 장치만 있어 어긋난다.
  - Input System 1.20 부터는 가로챈(handled) 이벤트도 장치 상태를 갱신하는 것이 기본이라, 기록 동안만 예전 처리로 돌려놓고 끝나면 되돌린다.
  - 그래도 실제 장치가 눌린 것으로 보이면 기록을 그 자리에서 실패로 끝낸다("실제 장치 입력을 가로채지 못해…"). 플레이를 다 하고 나서야 어긋난 것을 알게 되지 않게 하기 위해서다.
- 가상 장치는 세션을 시작할 때 실제 장치마다 미리 만들고, 그 목록을 기록에 남긴다. 재생도 같은 장치를 같은 순서로 만든다.
  - 첫 입력이 올 때 만들면 그 순간 Input System 이 액션 바인딩을 다시 풀면서 이미 움직인 컨트롤(마우스 위치 등)을 한 번 더 발사한다. 그게 방금 들어온 첫 터치와 같은 프레임에 겹치면 UI 는 마우스 입력으로 보고 터치를 버린다.
  - 재생은 장치가 처음부터 있어 그 일이 없으므로, START 를 누르고 게임 화면으로 돌아와 한 첫 드래그가 녹화에서만 안 먹었다.

### 앱 포커스

- 앱이 포커스를 잃거나 되찾을 때 스크립트가 받는 알림(`OnApplicationFocus`·`OnApplicationPause`, `Application.focusChanged`)을 세션 동안 막고, `Application.isFocused` 는 늘 true 로 준다.
- 게임은 이 알림에서 서버 시각을 다시 맞추거나 화면을 새로 고치곤 한다. 요청이 하나 더 나가면 그 뒤 응답 순서가 밀려 플레이가 갈린다.
- 기록에 남지 않는 입력이라 재생에서 되살릴 수 없으므로, 기록 때도 재생 때도 게임은 계속 포커스가 있다고 본다.

### 로딩 시간 차이

- 씬·Addressables·비동기 작업 완료를 기록해, 재생 때 같은 로딩이 끝날 때까지 게임 시간을 멈춘다(씬은 실제로 읽는 중일 때만. 기다린 프레임의 난수 소비는 되돌림).
- Addressables 로딩은 이름으로 짝짓는다. 개수만 세면 재생에만 있는 로딩이 하나 끼는 순간부터 그 뒤가 모두 한 칸씩 앞서 짝지어져, 늦게 끝난 로딩을 기다리지 못한다.
  - 이름이 다른 로딩(언어마다 다른 글꼴·테이블)은 같은 종류(작업·에셋 형식)끼리 짝짓는다.
  - 그것도 없으면 최근 1초 안에 끝난, 기록에 없는 로딩과 짝짓는다(초기화 방식 차이 등).
  - 이전 형식 기록처럼 로딩 이름이 없으면 예전대로 개수로 맞춘다.
- 씬을 일찍 다 읽으면 기록 때 열린 프레임까지 활성화를 미룬다.
- 완료 콜백 안에서 시작해 바로 끝난 다음 로드는 다음 프레임으로 미루지 않고 같은 프레임에 이어서 끝낸다(연쇄 단계 수가 언어마다 달라도 걸리는 프레임이 같게).
- **Simulated Load Delay**: 에디터의 Addressables(Use Asset Database)가 로드마다 넣는 가짜 지연은 세션 동안 0 으로 둔다. 실제 빌드에는 없는 지연이고 시계에 묶여 있어, 로딩 대기와 얽히면 로드가 안 끝나거나 일찍 끝난다.
- **기다리는 동안의 시계**: 세션 시계로 끝나는 것(`Task.Delay`, 테이프 응답)도 같이 멈춘다. 로딩만 늦은 것이면 풀린 뒤 녹화와 같은 프레임에 이어진다.
- **2초 넘게 안 풀리는 대기**: 씬·서버 응답이 아닌 로딩을 2초 넘게 기다려도 안 풀리면 그 시계들을 따로 돌려 풀고, 결과에 "로딩" 으로 남긴다. 그 로딩으로 가는 길에 대기·응답이 있는 경우이고, 흐름이 이미 녹화와 다르다.
- **엔진 시간 보정**: 기다리는 프레임마다 게임 시간이 아주 조금(2^-17초) 흐르는데, 대기가 풀린 다음 프레임을 그만큼 짧게 해 되돌린다. 엔진 시간(`Time.time`)이 녹화와 다시 같아져, `Time.time + 1초` 처럼 프레임 경계에 딱 걸리는 게임 타이머가 한 프레임 일찍·늦게 끝나지 않는다.

### 언어 전환

- 저장 값 안의 녹화 언어 표기(ko-KR·Korean 등)를 재생 언어로 바꾸고, 기기 언어와 UI 문화권(CurrentUICulture)도 그 언어로 둔다.
- 그래도 다르면 부팅이 끝난 뒤(START 이후) Unity Localization·I2 선택 언어를 바꾼다.
- 도구가 선택 언어를 읽을 때는 게임이 언어 시스템 초기화를 끝낸 뒤에만 읽는다(Unity Localization 은 읽기만 해도 진행 중인 초기화를 그 자리에서 끝낸다).
- 그 언어로 처음 뽑느라 실제 서버에서 받은 응답이 있었던 패스는 받아 둔 응답으로 한 번 더 뽑는다(결과에 "다시 —").

### BGM·SFX 분리

- 반복 재생하는 10초 이상 소리를 BGM 으로 보고 패스마다 끈다.

### 재생 속도

- 재생 동안 Game 뷰를 최대화한다(다른 창이 매 프레임 그리지 않게, 끝나면 되돌림).
- 영상에 남지 않는 구간(START 전·스템 패스)은 URP 렌더 스케일을 0.1 로 낮춰 그린다(화면 좌표·UI 레이아웃은 그대로).
- 패스마다 걸린 시간은 콘솔에 `재생 …프레임에 …초` 로 남는다.
- 런타임 패치 대상은 `Library/LocaleCapture/patch-targets.json` 에 캐시해, 코드가 다시 빌드되기 전까지 녹화 대기가 바로 끝난다.
